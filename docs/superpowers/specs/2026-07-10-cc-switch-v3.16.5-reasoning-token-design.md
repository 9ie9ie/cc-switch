# CC Switch v3.16.5 Reasoning Token Display Design

## Goal

Port the existing Codex reasoning-token display from commit `2a4c131a` onto the official CC Switch `v3.16.5` release without bringing across the unfinished standalone reasoning analytics work.

## Scope

The new build will:

- Read reasoning-token counts from supported Responses and completion usage fields.
- Preserve reasoning-token counts while importing Codex session JSONL logs.
- Store the count in request logs and daily usage rollups.
- Return the count through the existing usage API.
- Show `推理 <count>` under the output-token value in the request log table.
- Render `516`, `1034`, `1552`, and `2070` in red, matching the current `518n - 2` rule for `1 <= n <= 4`.
- Keep database schema version 12 so the existing `C:\Users\13164\.cc-switch\cc-switch.db` remains compatible.

The new build will not include the uncommitted `codex_reasoning_events` index, reasoning summary API, analysis script, or a new statistics page.

## Migration Approach

Create a clean worktree and branch from tag `v3.16.5`. Cherry-pick the existing feature commit `2a4c131a`, then resolve conflicts against the new upstream code by preserving upstream behavior and applying only the scoped reasoning-token changes.

The current `codex/reasoning-token-display` worktree contains unrelated uncommitted files and will remain untouched.

## Data Flow

1. Proxy responses and Codex session logs expose usage details.
2. Backend parsers normalize `reasoning_output_tokens`, `output_tokens_details.reasoning_tokens`, and `completion_tokens_details.reasoning_tokens` into one field.
3. SQLite stores the normalized value in request logs and daily rollups.
4. The usage command returns `reasoningOutputTokens` to the frontend.
5. The request log table displays the value and applies the existing warning predicate.

Missing reasoning data remains zero and is not displayed. Existing rows are not fabricated or backfilled unless the source log already contains the value.

## Database Compatibility

Official `v3.16.5` still uses schema version 11. The custom build will retain schema version 12 and the existing migration that adds reasoning-token columns. It must open the current v12 database directly and must not downgrade or recreate it.

## Verification

- Run the focused request-log table tests, including normal, zero, and warning values.
- Run TypeScript type checking.
- Run Rust tests or focused backend tests covering usage parsing and session import.
- Run `cargo check` for the Tauri backend.
- Build the Windows package through the fork's GitHub Actions workflow.
- Launch the new executable against a backup or the existing v12 database and confirm the request-log table renders reasoning values.

## Delivery And Rollback

Push a dedicated branch to `9ie9ie/cc-switch` and build a separate Windows artifact. Install it in a new directory on drive E before replacing any existing executable. Keep both the current custom build and the official installation available for rollback; the official v11 build still cannot open the v12 database without restoring a v11 backup.
